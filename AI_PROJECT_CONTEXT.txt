PROJECT OVERVIEW
================

Project/package: schoolmate
Purpose: Flutter school/institution management application UI. The repository
contains an institution-admin dashboard and many management pages, as well as
student/teacher dashboard placeholders. Many management pages are UI prototypes;
do not assume their displayed sample data is connected to a backend.
Application type: Flutter app (Android, iOS and macOS platform folders exist).
Language: Dart; pubspec.yaml requires Dart SDK ^3.13.4.
Detected toolchain: Flutter 3.49.0-1.0.pre-83 (local environment, 2026-10-05).
State management: flutter_bloc. AppBloc currently manages only locale and theme.
Many interactive presentation pages use StatefulWidget/setState. There are no
feature data Blocs/Cubits or repository flows in the current source files.
Routing: go_router, configured as a flat GoRouter route list.
Dependency injection: no registration/resolution framework found. main.dart
manually creates SharedPreferences and passes it to AppBloc.
Backend/API: no concrete backend integration found. ApiClient and NetworkInfo
are interfaces/placeholders; NetworkInfoImpl always returns true. No configured
base URL, endpoint implementations, repository implementations or API/domain
DTO layer was found in lib/. Some pages define private presentation-only sample
models; these are not wired as a shared data/domain layer.
Local storage: shared_preferences, used for language_code and theme_mode only.
Authentication: not implemented. Login route is a placeholder screen; there is
no token/session storage, auth state or router guard.
Localization: Flutter gen-l10n; English (en) and Bangla (bn).
Theme: Material 3 ThemeData with light/dark themes, AppBloc ThemeMode switching.

Notable dependencies (pubspec.yaml): flutter_bloc, equatable, go_router,
shared_preferences, flutter_localizations, intl, google_fonts, table_calendar,
cupertino_icons. No HTTP client dependency is currently declared.

ARCHITECTURE AND CURRENT IMPLEMENTATION
=======================================

The source is organized by feature and presentation responsibility, but this
is currently primarily a UI prototype, not a fully implemented clean/data
architecture. Do not infer implementations from empty data/domain directories.

Current app configuration data flow:

  main()
    -> SharedPreferences.getInstance()
    -> BlocProvider(AppBloc(prefs))
    -> MyApp / BlocBuilder
    -> MaterialApp.router(locale, themeMode, AppRouter.router)

AppBloc reads language_code (default "en") and theme_mode (default "system")
from SharedPreferences during construction. ChangeLocaleEvent and
ChangeThemeEvent update the matching preference and emit AppState. AppState
contains Locale and ThemeMode. AppState.initial() separately declares Bangla,
but main uses AppBloc's preference loader, whose first-run locale is English.

For most screen data there is no central data flow: pages use inline sample
values, local widget state, static UI and/or placeholder content. ApiClient has
get/post/put/delete method contracts only. NetworkInfoImpl reports connected
unconditionally. No API-to-model-to-repository-to-feature-state path is wired.


NAVIGATION FLOW
===============

Router: lib/core/routes/app_router.dart
Route constants: lib/core/routes/app_routes.dart
Router type: GoRouter with a flat list of GoRoute entries and an errorBuilder.
Initial location: AppRoutes.initial, which is SplashPage.routeName ("/").
No redirect/auth guard, nested route tree or deep-link configuration was found.

Current onboarding path:

  "/" SplashPage
    -> waits about 2 seconds
  "/onboarding" OnboardingPage
    -> skip or finish onboarding
  "/role-selection" RoleSelectionPage
    -> "/student-dashboard"
    -> "/teacher-dashboard"
    -> "/institution-admin-dashboard"

The login route "/login" exists as inline placeholder UI. It is not part of
the automatic splash/onboarding route path. Settings logout navigates to it.
Many institution-admin pages are individually registered in app_router.dart;
app_routes.dart stores their route names. Most navigation calls use context.go,
context.push or context.pop. Route definitions are flat, not nested.

The shared bottom navigation is currently presentation-only; its onTap handler
does not navigate. Verify behavior before assuming its displayed destinations
work.

STATE MANAGEMENT
================

AppBloc
  Location: lib/core/bloc/app_bloc/
  Purpose: application locale and ThemeMode preferences only.
  Events: ChangeLocaleEvent(Locale), ChangeThemeEvent(ThemeMode).
  State: AppState(locale, themeMode), Equatable.
  Persistence: SharedPreferences keys language_code and theme_mode.
  Consumer: MyApp listens via BlocBuilder; language/theme controls dispatch
  events through context.read<AppBloc>().

Other current state is generally page-local StatefulWidget/setState (examples:
onboarding page index, role selection, calendar selection/range and account
security selected tab). Do not create another global state system without
checking current feature needs and discussing the integration pattern in code.


API, ERRORS, STORAGE AND AUTHENTICATION
=======================================

API/network:
- lib/core/network/api_client.dart: abstract CRUD-like HTTP contract only.
- lib/core/network/network_info.dart: interface and placeholder implementation
  returning true; no connectivity package is declared.
- No concrete API client, base URL, endpoint, repository, remote data source,
  data model/DTO or API auth header handling found.
- lib/core/errors defines Server/Cache/Network exceptions and Failure types,
  but no feature repository conversion path is wired.

Storage:
- SharedPreferences is the only observed application persistence mechanism.
- Stores language_code and theme_mode from AppBloc.
- No token, user session or business records are persisted by current app code.
- No SQLite/Hive/Isar/SecureStorage implementation found.

Authentication:
- Login is placeholder UI. There is no credential flow, token, secure storage,
  session restoration or auth route guard in current implementation.
- Role selection is a UI choice that navigates directly to a dashboard.

Dependency injection:
- No DI package or registration module exists. SharedPreferences is manually
  obtained in main.dart and passed to AppBloc. Other UI dependencies are
  imported/constructed directly.


THEME SYSTEM
============

Files:
- lib/core/theme/app_theme.dart: AppTheme.lightTheme and darkTheme; Material 3,
  ColorScheme, TextTheme and component defaults.
- lib/core/theme/app_colors.dart: current palette and semantic accent/status
  colors.
- lib/main.dart: assigns theme, darkTheme and Bloc-driven themeMode to
  MaterialApp.router.
- lib/core/bloc/app_bloc/: dispatch/persistence of ThemeMode preference.
- lib/features/settings/presentation/widgets/theme_dialog.dart: UI for
  light/dark/system mode selection.

Primary brand purple is #6200E8 in light and dark themes. ThemeMode defaults to
system if SharedPreferences has no theme_mode value. Theme-dependent screen
colors should use Theme.of(context).colorScheme, textTheme, scaffold background
and component themes. Keep explicit fixed colors only for intentional semantic
status/data visualization or illustration colors, and verify dark contrast.
Change shared defaults in AppTheme/AppColors rather than duplicating palette
values throughout pages.

DEVELOPMENT RULES / COMMON PITFALLS
==================================

1. Inspect the actual page, route, widget references and state before changing
   architecture; many similarly named pages are distinct.
2. Reuse existing widgets and AppBloc locale/theme state. Do not invent feature
   Blocs, repositories, API endpoints, authentication or persistence as if they
   already exist.
3. Keep feature widgets with their owner; use core/widgets only for real
   cross-feature widgets. Never create lib/widgets/.
4. Keep core widgets independent of feature-specific UI.
5. Use ThemeData/ColorScheme/TextTheme for theme-dependent colors.
6. Keep status colors semantic and ensure readable light/dark contrast.
7. Preserve navigation, UI and business behavior unless explicitly asked to
   change them. Existing UI callbacks may be placeholders/no-ops; do not claim
   functionality based only on labels.
8. Prefer AppLocalizations where translations exist; keep English and Bangla
   ARB entries aligned.
9. Update GoRouter route table and AppRoutes constants when adding a page; check
   whether the route needs to be discoverable from drawer/menu UI.
10. Search references before moving a widget; update imports and verify no old
    path remains. file_path.dart is a broad legacy barrel and can hide imports.
11. Keep SharedPreferences usage limited to appropriate small preference data;
    the current app only persists locale and theme.
12. Run flutter analyze lib after structural edits. Run tests when requested or
    when required by the task; inspect the existing test before assuming scope.


HOW TO ADD A FEATURE (CURRENT PROJECT SHAPE)
============================================

1. Choose the existing feature folder (or create one under lib/features/).
2. Put pages in that feature's presentation/pages/ and related UI in its
   presentation/widgets/. Keep one-off helpers local where practical.
3. Use core/widgets only if usage crosses unrelated features.
4. If the page needs app-wide locale/theme, use the existing AppBloc. For new
   business state, first establish the required data source and feature state
   flow; none is currently wired for the existing admin sections.
5. Add route path in AppRoutes and a GoRoute in AppRouter. There are no guards.
6. Add user-facing translations to both ARB source files where appropriate.
7. Use the existing ThemeData/ColorScheme and check both brightness modes.
8. Verify imports, run flutter analyze lib, and update this document if folder,
   routing, state, storage or dependency architecture changes.
